# SAND OS Integration

NOCTIS has a dedicated SAND OS integration target under `sand-app/`. It
produces an **SAPP v1** native application container using the current
`jadhavdurvesh/sand-apps` packer and inspector.

## Repositories and ownership

- [SAND OS](https://github.com/jadhavdurvesh/sand-os) owns the kernel,
  process loader, syscalls, graphics, storage and future application ABI.
- [SAND Apps](https://github.com/jadhavdurvesh/sand-apps) owns the SAPP
  application format tooling, manifest conventions, validators and app
  workspace.
- [NOCTIS](https://github.com/jadhavdurvesh/noctis) owns its browser engine
  and this small SAND integration probe.

The NOCTIS workflow checks out a pinned SAND Apps commit so a future change
in the packer cannot silently change the package generated by an older NOCTIS
commit. Update the pinned commit intentionally after reviewing the format
and ABI changes in SAND Apps.

## Actual package target

The current SAND loader contract is:

| Field | Current requirement |
|---|---|
| Package | SAPP v1 |
| Architecture | x86-32 / i386 |
| Header | 64 bytes |
| Segment record | 32 bytes |
| Relocation record | 12 bytes |
| Segment count | 1–8 |
| Total mapped image | Up to 64 pages |
| User address range | 0x40000000–0xBFFFFFFF |
| User stack top | 0xBFFFE000 |
| Permissions | Read required; W+X rejected |
| Signature | Not supported; development packages unsigned |

The packager is not simply renaming ELF to `.sapp`. It reads a constrained
little-endian ELF32/i386 executable, extracts loadable segments, creates SAPP
metadata/header/segment records, and the inspector validates the final
container. The source of truth is the current SAND Apps `FORMAT.md`,
`tools/sapp_pack.py`, and `tools/sapp_inspect.py`, together with the SAND OS
`process_create_sapp()` loader.

## NOCTIS SAND probe

The source in `sand-app/` deliberately builds one read/execute segment at
0x40000000. Its entry calls only the existing ring-3 test operation:

- EAX = 1
- EBX = 0x53414E44

That is a kernel test hook, **not a stable public userspace ABI**. The probe
then idles. It demonstrates that NOCTIS can produce a container the SAND
Apps inspector accepts; it does not prove normal app installation, launch
from the OS filesystem, terminal output, UI rendering, or browser operation.

## Workflow

`.github/workflows/sand-os-app.yml` runs when SAND probe sources or related
workflow/docs change, and on manual dispatch. It:

1. Checks out NOCTIS.
2. Checks out the pinned SAND Apps tooling.
3. Builds a freestanding x86-32 ELF executable.
4. Packages that ELF into SAPP v1 with the SAND Apps packer.
5. Inspects the result and asserts x86-32, one R/X segment, and zero relocations.
6. Uploads the `.sapp` package, ELF intermediate, manifest and probe README
   as a GitHub Actions artifact.

The artifact is a development package and is not signed. The current SAND OS
does not yet provide a general public app installation/launch command.

## What a real browser port still needs

The kernel currently accepts only a fixed test syscall from ring 3. It does
not yet provide a stable public API for the services required by a browser:

- Window creation, input events and a presentable graphics surface.
- Console/text output and robust process termination.
- Filesystem APIs, file descriptors and safe user-pointer copying.
- Networking, sockets and TLS.
- Timers, event notification and process lifecycle services.
- A documented, versioned userspace ABI and a secure package trust/signing
  policy.

Those APIs must be implemented and tested in SAND OS first. NOCTIS must then
add a SAND platform backend that uses those documented services. Do not use
undocumented syscall numbers or assume the current test hook is a production
application interface.

## Build locally

With GNU Make, Python 3, GCC/binutils with i386 support, and a checkout of
SAND Apps available beside the NOCTIS repository:

```sh
make -C sand-app clean all SAND_APPS_SDK=../sand-apps
```

The output is `sand-app/build/noctis-engine-probe.sapp`.
